# niubigeo 复用与实现路线

核对日期：2026-10-29。本文保留集成设计；上游已下载到 vendor 并通过本地检查，0.1.0 的实际范围见 [当前实现](04-local-prototype.md)。

## 1. 推荐的接入方式

采用 **独立项目名与仓库、基于 niubigeo 稳定版本派生开发** 的方式。继续维护上游来源和版本记录，将新增业务流程放在独立模块中。

原因是上游已有可用的测量、连接和展示基础，适合个人尽快做出完整业务样例。本项目的主要新增工作放在资料确认、策略执行与实验，而模型适配和历史观测可以延续已有实现。

最小方案是先只导入上游归档：人工提供品牌资料和回答，生成诊断、任务和报告。这一版无需模型账号，已经能验证工作流是否有用。

另一个可选方向是完全独立建设核心，通过外部服务接入 niubigeo。其优势是边界清楚，但需要维护两个产品的数据协议与运行状态。当前单人阶段优先派生开发；如果以后出现多个测量后端，再把内部适配边界提取成外部协议。

## 3. 复用边界

| 能力 | 已核对的上游位置 | CiteKeel 的使用方式 |
| --- | --- | --- |
| 产品服务与项目组织 | `src/product/product-server.ts`、`src/product/projects/` | 沿用服务入口与项目基础，新业务数据独立保存 |
| 模型连接 | `src/product/connections/`、`src/product/recognition/recognition-service.ts` | 复用已连接模型的执行器；保留实际端点与搜索信息 |
| 配置与观察范围 | `src/product/configuration/`、`src/product/measurements/watchset-service.ts` | 将确认后的业务问题映射为测量范围，保留映射版本 |
| 测量与归档 | `src/product/measurements/measurement-service.ts`、`measurement-schema.ts` | 通过适配层转成本项目统一样本；记录原始 ID |
| 来源提取 | `src/providers/citation-extractors.ts` | 沿用提取逻辑，在业务统计前再次区分 provenance |
| 统计与比较 | `src/product/measurements/measurement-stats.ts` | 复用明确核对的能力；本项目实验指标单独保留公式、样本清单和版本 |
| 归档样例 | `examples/cases/` | 用于回放与兼容性核验，明确是上游历史数据 |
| 定时执行 | `src/product/scheduling/` | 在手动闭环通过后接入，默认关闭定时任务 |

上游 `package.json` 标记 `private: true`。本方案将其作为源码基础，不假设存在可直接安装的稳定 SDK 包。

## 4. 需要按源码重新判断的地方

部分上游文档仍描述早期状态。例如架构文档写当前产品只走 OpenRouter，但固定提交的认知执行器已包含自定义连接分支。测量统计也已选择 latest attempt，并非旧限制文档描述的 first attempt。不能把旧文档中的每项限制直接当作当前版本缺陷。

已核对的代码入口：

- [认知执行器](https://github.com/Albert-Weasker/niubigeo/blob/dd51eedc8e400006755639c0cb332a7fa1a71420/src/product/recognition/recognition-service.ts)
- [测量服务](https://github.com/Albert-Weasker/niubigeo/blob/dd51eedc8e400006755639c0cb332a7fa1a71420/src/product/measurements/measurement-service.ts)
- [测量统计](https://github.com/Albert-Weasker/niubigeo/blob/dd51eedc8e400006755639c0cb332a7fa1a71420/src/product/measurements/measurement-stats.ts)

源码仍提示三项与本项目直接相关的边界：

1. 测量服务构造 `providerCitations` 时会排除正文 URL，但仍需检查保留下来的来源类型；集合名字本身不能证明是答案引用。
2. 当前测量流程中，派生结果的保存与含原文的终态 Attempt 保存存在先后顺序。CiteKeel 应先确认原文归档完整，再让样本进入报告。
3. 上游已有费用限制与未知费用阻断逻辑，但检查阈值不等于下一次请求最大费用已预约。本项目不能在未经验证时承诺精确的账户费用上限。

这些是接入时的检查要求，不是本次已经完成的漏洞复现或回归测试。

## 5. 新增能力怎样嵌入

拟新增以下目录；这是实现文件边界设计，目前没有创建代码脚手架：

| 目录 | 职责 |
| --- | --- |
| `src/citekeel/domain/` | 事实、问题版本、任务、发布与实验对象 |
| `src/citekeel/workflow/` | 状态转换、前置条件、暂停与恢复 |
| `src/citekeel/skills/` | 八项语义任务的调用与输出校验 |
| `src/citekeel/adapters/` | 上游结果、人工记录与归档数据的转换 |
| `src/citekeel/evidence/` | 原文与判定关联、来源类型检查、导出 |
| `src/citekeel/experiments/` | 实验清单、固定样本、指标和报告 |
| `skills/` | 可独立阅读和复用的 Skill 说明与示例 |
| `examples/synthetic-sensor/` | 全新合成的 B2B 示例 |

不将本机已有 Skill 的绝对路径、个人写作素材或登录工具写成用户安装依赖。`a2w` 的选路思想可以用于本项目的信源收集策略；开源版本使用标准的工具接口和配置，避免要求使用者先复制作者的工作环境。

## 6. 测量适配约定

适配器接受三种来源：上游归档、人工导入、实时 API。它们都转换为同一业务样本结构，并保留来源标签。

每条样本至少含：项目 ID、问题版本与问题 ID、协议 ID、计划样本 ID、尝试 ID、入口类型、模型与端点、时间、原文、来源项、采集状态、分析状态和上游定位信息。

上游以域名识别和中性关键词发现组织探针，本项目的问题空间还包含自由问句。因此不假设上游默认提示词可以直接表达所有问题。适配层必须保存“业务问题 → 实际发送提示词”的映射，诊断报告以实际发送内容为准。

消费级网页、官方 API、第三方路由 API、受控上下文实验和历史归档各自分组，不合成一个平台推荐率。人工输入网页观察时保存会话条件与可核对的原文位置。

## 7. 执行与恢复规则

- 新测量先生成固定计划清单，再执行；失败不会减少 planned 数。
- 原始响应先保存，语义分析在其后运行。分析失败可以重做本地判定，默认不重新调用采样模型。
- 重试新增 Attempt，旧原文保留。采集失败和分析失败使用不同状态。
- 首版只允许一个写入者。处理中断后展示未完成步骤，由操作者恢复；不承诺外部 API 恰好调用一次。
- 成本状态未知时暂停后续付费请求；同时使用 Provider 侧额度上限。请求数上限与金额上限分开记录。
- API 不可用时仍可导入记录和回放报告；网页不可访问时保留当时引用记录及本次访问状态。

## 8. 实现顺序

| 阶段 | 可独立使用的结果 | 验收 |
| --- | --- | --- |
| A：资料与归档闭环 | 合成资料、问题确认、导入回答、诊断、任务、Markdown 报告 | 无 API Key 可走完整流程，所有判断可定位到输入 |
| B：实时观测 | 接入一个模型 API，保存完整尝试记录，比较两轮结果 | 请求失败、解析失败、别名误判与搜索未知均有明确状态 |
| C：内容与交付 | 基于事实生成内容，审核，人工登记发布，复测并复盘 | 一个任务贯穿问题、事实、内容版本、发布链接和结果 |
| D：实验与公开样例 | 受控实验报告、公开回放包、线上观察协议 | 同口径复验，导出不含私人材料，结果与限制同时展示 |

A 阶段是最小可交付版本。B、C、D 的每个阶段都能独立合入，不以后一阶段完成作为当前阶段可用的前提。

估计首个端到端原型需要个人 7–12 个有效工作日，取决于上游接入与数据兼容情况。线上观察另需要数周等待与采样，不能计为几天内必然验证优化有效。

完整实现预计超过 8 个文件，但只增加现有 Node 进程内的模块，不新增独立服务。第一版暂不加入收费、多人权限、自动外部发布或全平台浏览器采集。

## 9. 依赖与验证

| 依赖 | 作用 | 本次状态 |
| --- | --- | --- |
| niubigeo 固定提交与公开样例 | 源码基础和归档兼容 | 已通过 GitHub 连接读取 |
| Node / npm | 构建与运行 | 已核对上游要求；尚未安装或运行本项目依赖 |
| 模型 API Key | 新测量与 Skill 生成 | 离线版本不需要；本次没有读取密钥或发起计费请求 |
| OpenRouter 连接 | 首个实时接入候选；沿用 `OPENROUTER_API_KEY` 配置 | 已有上游历史归档，当前账号与模型执行未预检 |
| 自有发布位置或人工发布渠道 | 线上观察的干预载体 | 原型支持人工登记，不依赖发布账号接入 |

实时执行的模型 ID、费率、原生搜索与结构化输出兼容性必须在运行前预检，并写入实验协议；历史归档中的模型名称不能当作当前可用性的保证。若预检失败，阶段 A 的交付仍可使用。

引入上游后，先运行它已有的 `npm run self-check`。新增验证覆盖：事实冲突阻塞、问题版本隔离、正文链接与引用区分、失败样本分母、重试留痕、发布状态、归档回放和导出字段过滤。测试脚本应随实现加入；当前文档不把拟议脚本写成已经可运行的命令。

回退方式：保留上游原数据，只向新业务目录写入；关闭新增入口即可继续使用原观测能力。外部内容变更保留发布版本，恢复时登记回退时间，不覆盖旧实验记录。
