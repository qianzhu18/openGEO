# GEO 到底在做什么：建站、内容、平台、抓数与发布边界

日期：2026-11-02。回答四个问题：国外 GEO 是不是就是建站/写文章；Reddit、LinkedIn 发什么、监控什么；数据怎么抓、方案怎么出；开源项目要不要"独立云电脑"。

文中"Topify 实证"指我们登录后实际看到的页面/接口与官方文档；"行业做法"是通用工程判断，不是对某家产品的验证。

## 1. 先纠正：GEO 不是"建站"，是"让 AI 有东西可引用"

AI 回答一个品类问题时，会做三件事：检索 → 选源 → 组织答案。你能影响的只有"选源"：

- **它读得到你的页面吗**（可抓取、结构清晰、事实明确）；
- **它信得过你的页面吗**（谁写的、有没有数据、有没有被第三方引用）；
- **它在别处见过你吗**（Reddit、G2、媒体、LinkedIn、GitHub、文档站）。

所以主站是**必要条件和底座**，不是全部。建站 ≠ GEO；文章也只是内容形态之一。

### 国内 vs 国外，逻辑像但载体不同

| | 国内 GEO | 国外 GEO |
| --- | --- | --- |
| 主战场 | 百家号、头条、知乎、公众号、小红书 | 自有博客/文档站 + Reddit + LinkedIn + YouTube + G2/Trustpilot + 行业媒体 |
| 平台角色 | 平台内分发，平台即入口 | 平台是"第三方证据"，最终仍导回官网 |
| 可控资产 | 账号（可能被封） | 官网（完全可控）+ 邮件列表 |
| 抓取难度 | 平台封闭，多靠人工/半自动 | 网页可抓，但登录、地区、反爬更复杂 |
| 核心动作 | 铺量 + 平台权重 | 可引用的事实 + 第三方提及 + 结构化 |

结论：国内更像"平台运营"，国外更像"内容 + 公关 + 技术可抓取"的组合。**说"国外 GEO 就是写文章"是不准确的，说"就是建站"也不准确。**

## 2. 国外 GEO 具体做什么（不只文章）

按优先级：

1. **技术可抓取**：robots.txt 允许 GPTBot/ClaudeBot/PerplexityBot；sitemap；服务端渲染；`llms.txt`（可选，不是银弹）；结构化数据（Organization、Product、FAQPage、Article）。
2. **实体一致性**：品牌名、一句话描述、官网、logo、社交账号在所有地方一致；否则 AI 会把你和同名事物混淆。
3. **可引用的事实页**：pricing、compare、docs、changelog、security、case study——AI 最爱引用"有具体数字和明确边界"的页面。
4. **内容格式**：answer-first（先给结论）、每条主张带来源、统计数字、专家引述、FAQ、表格对比。
5. **第三方提及**：Reddit 真实讨论、G2/Capterra 评价、行业媒体、LinkedIn 观点、YouTube 演示、GitHub/文档。
6. **监控**：AI 答案里的提及/位置/情感/引用；引用来源里谁在赢；竞品在哪些问题里出现。

## 3. Reddit 和 LinkedIn：发什么、监控什么

### Reddit

**发什么**（不是发广告）：

- 回答具体问题：有人问"X 和 Y 怎么选"，给可验证的对比、价格、限制；
- 分享真实数据/踩坑：迁移成本、失败案例、性能数字；
- 在相关 subreddit 做 AMA 或答疑；
- 引用自己官网的具体页面（不是首页）。

**监控什么**：

- 品牌/竞品被提及的 thread 与语境（推荐 / 吐槽 / 对比）；
- 谁在回答里被反复推荐（这是 AI 也会读的"社区共识"）；
- 负面情绪与事实错误（可回复纠正，但不能刷）；
- 链接与引用：你的页面有没有被贴进讨论。

**怎么抓**：Reddit 公开 JSON（`/r/xxx/search.json`、`/comments/xxx.json`）优先；网页抓取作为兜底；注意速率限制与 ToS。

### LinkedIn

**发什么**：

- 创始人/团队的观点与复盘（带数字）；
- 客户案例、迁移故事；
- 产品更新、行业数据解读；
- 员工转发形成"多点提及"。

**监控什么**：

- 品牌提及与情感（LinkedIn 搜索 + 通知）；
- 竞品对比帖、行业讨论；
- 哪些帖子带来官网流量（UTM）。

**怎么抓**：LinkedIn 反爬严格、无公开搜索 API。现实做法是**人工/半自动**：保存帖子和截图、手动登记；不要指望稳定自动化。Topify 也没有 LinkedIn 集成。

## 4. 数据怎么抓：三层 + 四种手段

### 三层数据

| 层 | 内容 | 用途 |
| --- | --- | --- |
| 引擎回答 | ChatGPT、Perplexity、AI Overview、Gemini、Claude 对问题的回答 | 提及、位置、情感、引用 |
| 引用来源 | 回答里的 URL、搜索来源、grounding | Sources 分析、找"AI 信任谁" |
| 平台内容 | Reddit、G2、LinkedIn、媒体、竞品站 | 选题、第三方证据、舆情 |

### 四种手段

| 手段 | 适用 | 优点 | 代价 |
| --- | --- | --- | --- |
| 官方 API | Claude、Perplexity、OpenAI（带 search 的模型） | 稳定、可计费、合规 | 与消费级网页答案不完全一致 |
| 浏览器自动化 | ChatGPT/Gemini/AI Overview 网页 | 接近用户真实所见 | 要登录态、地区、反封控、易碎 |
| 搜索 API | SerpAPI、Bing、Brave、Exa | 拿搜索结果与引用 | 不等于 AI 答案 |
| 爬虫/公开 JSON | 官网、Reddit、G2、文档 | 便宜、可控 | 反爬、ToS、结构变化 |

**Topify 实证**：ChatGPT / Perplexity / AI Overview / Gemini 用真实网页会话采集，Claude 走 API（官方文档自述）。这解释了为什么它必须有大量账号会话和地区出口。

### 抓取之后：判定

```text
原文 → 品牌归一化（名称/别名/域名/中文名/大小写）
     → 提及（去重品牌列表）
     → 位置（首次出现字符偏移排序）
     → 情感（每条回答每品牌一个 0–100 分）
     → 引用（URL / 搜索来源 / grounding，分 domain 与 URL）
     → 失败样本单独标记，不进分母
```

**品牌归一化是最容易翻车的一步**：名字撞词、缩写、中文名、子公司、产品名 vs 公司名。必须有人工维护的别名表和歧义标记。

## 5. 怎么出方案（不是"写一篇文章"）

一个可交付的 GEO 方案长这样：

1. **诊断**：哪些问题没出现、哪些来源在赢、竞品强在哪、你的页面缺什么；
2. **选题**：问题 × 意图 × 竞品缺口 × 商业价值，排序；
3. **内容 brief**：目标问题、要引用的来源、需要的数字/案例、结构（answer-first + FAQ + 对比表）、验收条件；
4. **生产**：模型起草（只用已确认事实）→ 人工审 → 改写；
5. **发布**：自有站可 API 发布；第三方人工发；
6. **复测**：固定问题版本、引擎、地区、时间窗，比较前后；披露混杂因素；
7. **复盘**：哪些动作有效、哪些是噪声、下一轮改什么。

**关键**：每个动作绑定证据 ID 与验收条件；没有证据的"建议"不进方案。

## 6. 发布边界：能不能替你发

| 渠道 | 能否代发 | 现实做法 |
| --- | --- | --- |
| 自有站（WordPress / Shopify / Framer / Ghost） | **可以**，走官方 API，需用户授权 | 审批后发布，记录回执与 URL；回执 ≠ 被引用 |
| Reddit | 不代发 | 生成回复草稿，用户自己发；平台风控严，自动发易封号 |
| LinkedIn | 不代发 | 生成帖子草稿；无公开发布 API，人工发 |
| 行业媒体 / 新闻稿 | 不代发 | 出 pitch 与素材，人工对接 |
| G2 / Capterra | 不代发 | 引导真实用户评价，不能刷 |

**Topify 实证**：CMS 只支持 WordPress / Shopify / Framer；`forum_engagement` 只产出 Reddit 回复草稿；没有 LinkedIn 自动发布。所以"第三方要用户自己发"基本成立；"完全不能发布"不成立——自有站可以代发。

对开源项目：默认**只产草稿 + 人工发布 + 回执登记**，不碰账号密码；CMS adapter 作为可选配置，由用户自己填凭据。

## 7. "独立云电脑"：需要，但不是字面意义的云电脑

### 对方用了什么

**没有证据**表明 Topify 用"独立云电脑"。官方只说"automated browser sessions against the same web UIs"。工程上通常是：

- 容器化 Chrome（headless / headful）+ 账号会话池；
- 固定地区出口（代理/云主机）；
- 任务队列 + 失败重试；
- 有时用云浏览器服务（Browserbase、Steel、Bright Data 等）。

叫它"云电脑"不准确，本质是**常开的浏览器执行环境 + 干净的出口 IP + 可管理的账号**。

### openGEO 要不要

分三阶段，不要一上来就买云电脑：

| 阶段 | 形态 | 适合 | 成本 |
| --- | --- | --- | --- |
| MVP | 用户本机 Chrome（CDP / ego lite）+ API | 验证、单次审计、演示 | 0 |
| 常开 | 一台 VPS（$5–20/月）跑 headless Chrome + 定时任务 | 每日监测、小团队 | 低 |
| 规模化 | 云浏览器/容器池 + 代理 + 账号管理 | 多客户、多地区 | 高，且要处理合规 |

**先做 API + 本机浏览器采集，再上 VPS 定时任务。** 直接上"独立云电脑"是把成本和风控前置，收益不确定。

### 真正要解决的四件事

1. **会话**：账号从哪来、怎么保持登录、封了怎么办；
2. **地区**：目标市场（US/GB）需要对应出口；
3. **稳定性**：页面改版、验证码、限流；
4. **合规**：平台 ToS、robots、个人信息。

这四件比"有没有云电脑"重要得多。

## 8. 给 openGEO 的最小架构

```text
adapters/
  api/        Claude、Perplexity、OpenAI(search)
  browser/    本机 CDP（ego lite / Chrome）、远程 Chrome、截图/HAR 导入
  search/     SerpAPI / Bing / Exa（可选）
collector/
  scheduler   cron：每天生成 run（幂等键）
  runner      run → job(问题×引擎) → attempt；预算/重试/超时
  judge       品牌归一化、提及、位置、情感、引用、失败样本
planner/      诊断 → 选题 → brief；绑定证据与验收条件
writer/       草稿（只用已确认事实）→ 审批 → 导出
publish/      CMS adapter（可选）+ 人工发布登记
report/       指标快照 + 证据链 + 复测对比
```

**部署**：本地 `npm start` → Docker Compose（app + chrome + volume）→ 托管。

## 9. 结论

1. GEO 不是"建站"，是"在 AI 会读的地方留下可引用的事实"；建站是底座，文章是形态之一。
2. 国外不等于"只写文章"：技术可抓取、实体一致性、第三方提及、结构化事实页同样重要。
3. Reddit/LinkedIn 发的是"真实、可验证、对别人有用"的内容；监控的是提及、语境、情感、链接。
4. 抓数据靠 API + 浏览器 + 搜索 + 爬虫组合；判定靠品牌归一化 + 引用解析 + 失败样本隔离。
5. 自有站可以代发；第三方只能出草稿，用户自己发——这是平台的边界，不是能力不足。
6. "云电脑"不是必需，**常开的浏览器执行环境**才是；先本机，再 VPS，最后才考虑云浏览器池。
