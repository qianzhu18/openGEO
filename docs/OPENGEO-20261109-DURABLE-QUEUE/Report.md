# 0.5.0 本地可靠执行

## 选型与参考链路

需要数据库持久化，不必因此安装 MySQL；需要任务队列语义，不必因此安装 RocketMQ。本仓库定位本机单用户，通常最多 10 题 × 5 平台，成本与上游限流是主要约束，没有分布式削峰的实测需求。SQLite 是有事务和崩溃恢复的关系数据库，不是内存缓存。

| 职责 | 本版实现（JS） | 分布式候选（未实现） |
| --- | --- | --- |
| 初始任务与查询 | SQLite runs/jobs/submissions，任务 ID，HTTP 202，前端轮询 | MySQL 任务/尝试/结果表 |
| 后台执行 | 本地进程后台 worker，目标内串行，Cloro 跨入口共享请求槽 | RocketMQ 消费者集群 |
| 原子状态写入 | SQLite BEGIN IMMEDIATE，运行、回执、任务状态同一快照事务 | MySQL 事务 + outbox，投递器 |
| 重复提交 | 项目内 requestKey 唯一，输入指纹冲突拒绝，同请求复用 run ID | 消费 inbox/唯一键 + 条件状态更新 |
| 失败处理 | 有限 429 退避、死信状态、费用待核对、人工重投 | 延时投递、DLQ、账单/请求查询核对 |
| 崩溃恢复 | 成功结果不重发，未知发送不自动重发，用户显式继续 | 消费恢复、租约与 fencing、外部请求对账 |

只有出现多个独立 worker/服务、跨进程任务分发、独立扩容或实际吞吐瓶颈，才重新评估 MySQL/RocketMQ；若用户要单独练习 Java 分布式后端，应独立实验，不把它描述成本地产品必须部署的依赖。MySQL+MQ 的业务提交和消息发送须经 outbox 或其他可证明一致性的机制，不把两次调用当成原子事务。ACK 应在结果提交后；重复投递通过唯一键与状态机处理。锁与 MQ 都无法保证第三方付费 HTTP 请求 exactly-once。

## 本版已实现

- 新 API-only 品牌诊断在返回任务 ID 前，冻结问题、平台、题集版本和协议指纹，生成一题×一平台任务。任务唯一性包含本轮 run；新一轮是新观测，重试不是新样本。
- `sampling.sqlite` WAL / synchronous FULL，运行快照（包含回执、样本、尝试）与 jobs 同事务提交；任务唯一键 `(run_id,unit_id)`，协议冲突回滚。删除 JSON 镜像后仍能读取数据库。JSON 镜像不是跨文件原子事务；若镜像写入失败，工作中止，数据库已提交数据仍可恢复。
- 本地服务启动先取 PID/token 单 worker 锁，再做中断恢复；第二个活进程拒绝使用同一数据目录。没有分布式租约，不支持多个消费者并发抢任务。
- 先保存领取与 lease token，再保存即将发送的 receipt，持久化成功后才发 HTTP。发送与数据库之间仍有不可消除的不确定窗口；恢复时缺少发送记录才允许继续，已经 attempted 的请求进入待核对。已落盘合格答案可恢复成功。
- 只对已留存 HTTP 429 且没有回答、generation ID、正费用记录的拒绝做有限退避；单轮最多 3 次尝试，15/30 秒基础退避加 jitter，尊重 Retry-After，超过 5 分钟等待上限转死信。不是所有 429 都重试；账单/额度类不会重试。不能保证上游没有收费。
- 超时/网络/空回答/截断等进入 review_required；认证、余额、参数错误等终止进入 dead_letter。目标入口失败后，其后问题暂停，不制造未发送的失败调用；其他目标可继续。OpenRouter 已有回答但费用未知也暂停后续题。Cloro 费用本来 UNKNOWN，保留其专用监测策略。
- 总计 64 次采样请求保护、Cloro 每目标 10 次监测保护包含重试与恢复。人工重投须明确确认费用风险，每任务最多一次，最多再领取 3 次（总数不超过 6），历史尝试与原文保留。同单元仍最多采纳一个结果。
- GET queue；POST stop / resume / redrive；中英文执行面板显示排队、请求中、退避、成功、死信、待核对与暂停，以及逐题原因。停止只阻止后续发送，不取消上游生成，不声称停止计费。进程重启不自动恢复付费请求；Key 只从当前服务商设置/环境读取，不入任务表。
- 持久队列诊断与恢复不自动执行额外策略/内容模型调用，保留本地规则产物与既有导出；策略质量提升仍后置。旧独立模式不在本轮改造范围。

## 验证

离线故障注入和浏览器回归，不是本轮真实付费 API 采样。`npm run build` 通过；`npm test` 142/142；`npm run test:browser` 28/28。

覆盖：429 后成功只贡献一个分母、耗尽转死信与后题暂停、超时不重发、SQLite 重开与无 JSON 读取、事务回滚、双 worker 拒绝、停止、人工重投保留尝试、重复提交复用与输入冲突、中英文费用确认和队列显示。

限制：Node 内置 SQLite 当前发 experimental 提示；依赖仓库 Node >=22.13；数据库使用同步接口，适合本地小规模任务。运行和回执在 snapshot JSON 列内，并非拆分后的通用分析仓库。全量历史迁移、结构化账单核销、定时调度、独立 worker 进程/集群、外部请求 exactly-once 均未实现。

## 困难记录与面试边界

最难的并不是把 HTTP 放到消息队列，而是判断“失败能不能再发”：429 有拒绝回执，超时却可能已生成和收费。我们先记录请求前后状态、原始响应与费用，然后才制定可重试分类；把不确定状态显式暴露，成功/失败/未知不混入统计。

可讲：从进程内循环演进到本地持久任务状态机，支持有限退避、死信、受控重投、重复提交去重和成功结果恢复。不能讲：用了 RocketMQ/MySQL、承受生产高并发、杜绝重复收费、实测提高成功率，或真实 GEO 发布后测闭环已经完成。
