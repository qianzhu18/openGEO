# 采集方式、失败原因与对标差异

日期：2026-11-02。回答三个问题：我们到底怎么抓页面、为什么有些站失败、和 Topify / niubigeo 差在哪。

## 1. 我们的抓取链路（当前实现）

```text
输入 URL
 → 校验（只允许 http/https、拒绝私网/凭据/非标准协议）
 → 服务端 HTTP fetch（DNS 固定、超时、大小上限、同域重定向检查）
 → content-type 必须是 HTML
 → cheerio 结构化提取（title / description / h1-h3 / 正文片段）
 → 回退提取（__NEXT_DATA__ 字符串 / meta / noscript / main·article 文本）
 → 若仍无文本：启动无头 Chrome 渲染一次（Playwright，禁图片/字体）
 → 再提取；仍为空 → 记录失败原因
 → 生成 sources / claims / topics / prompts
```

配置与限制：

- 单次研究总预算 25 秒，最多 3 个页面；
- 首页失败会再试一次 `www` / 裸域互换；
- 只采同域页面，跳转到站外直接判失败；
- 采集内容只作为“来源证据”，不自动当成已核实事实。

## 2. 为什么 `qianzhu.me` 之前失败、现在成功

失败不是网络问题：

- 它的服务端 HTML 只有一个空壳 `<div id="__next">`，`<title>`、description、正文都是空的；
- `__NEXT_DATA__` 里的 `pageProps` 也是空数组，内容由浏览器里的 JS 再请求/渲染；
- 旧逻辑只读静态 HTML → 没有可读文本 → 判失败。

现在的处理：

1. 静态 HTML 无文本 → 启动无头 Chrome 打开页面、等 JS 执行；
2. 从渲染后的 DOM 里取 `main/article` 文本；
3. 品牌名用 `og:site_name` / 标题，遇到 "Personal Blog" 这类通用标题则回退到域名（Qianzhu）；
4. 没有 meta description 时，从首个有意义的段落派生描述，并标注为来源证据。

实测结果：`qianzhu.me`（中文 / 中国）→ `completed`，品牌 Qianzhu，1 个主来源（约 2,500 字），4 个主题，6 条中文候选问题。

## 3. 失败分类（会显示在界面上）

| 原因 | 含义 | 下一步 |
| --- | --- | --- |
| `The URL did not return HTML.` | 返回的不是 HTML（PDF/图片/JSON） | 换页面或改用导入 |
| `No readable text` | 静态与结构化数据都没有文本 | 需要浏览器渲染 |
| `Redirect left the submitted domain` | 跳到了别的域名 | 用最终域名重新提交 |
| `Research time budget exhausted` | 25 秒预算用尽 | 重试或减少页面 |
| `Could not obtain usable public HTML evidence` | 传输失败/被拒 | 检查是否反爬或需要登录 |

界面会去重并显示“URL — 原因”，不再只给一句笼统错误。

## 4. “本地项目”是不是原因

**不是。** 本地 vs 云端只影响出口 IP、网络位置和是否常开；它不决定能不能执行 JavaScript。

- 静态抓取：本地和云端都是 HTTP 请求，能力一样；
- 动态页面：需要浏览器执行 JS，本机装个 Chrome 就能做；
- 真正的差别在账号、地区、反爬与稳定性，不在“本地”。

所以 `qianzhu.me` 这类站，本地照样能抓——前提是有浏览器渲染这一步。

## 5. 与 Topify 的差异

| 维度 | Topify | 我们 |
| --- | --- | --- |
| 站点研究 | 抓官网 + Semrush + 模型生成问题；云端浏览器 | HTTP + 无头 Chrome 回退；本地 |
| 回答采集 | 驱动真实消费级网页（ChatGPT/Gemini/AIO/Perplexity）+ Claude API | 目前 API 基线，浏览器采集待做 |
| 规模 | 每日全量、多项目、账号池、地区出口 | 单用户、手动触发、单机 |
| 数据 | 商业口径，部分算法不公开 | 全部本地、可回放、协议落盘 |
| 成本 | 订阅 + credits | 自己的模型 Key + 本机资源 |

Topify 强在“每天自动、规模化、消费级网页”；我们强在“本地、可审计、可改”。

## 6. 与 niubigeo 的差异

| 维度 | niubigeo | 我们 |
| --- | --- | --- |
| 测量 | API（OpenRouter）为主，测量纪律强 | API 基线 + 计划中的浏览器采集 |
| 站点研究 | 站点证据 + GitHub README，HTTP 抓取 | HTTP + 浏览器渲染回退 |
| 报告 | 强，人类可读、证据可追溯 | 有证据链，但还没它完整 |
| 调度 | cron + occurrence + 预算账本 | 还没做 |
| 定位 | 测量与报告 | 测量 + 动作 + 复测的交付闭环 |

niubigeo 明确不做消费级网页采集（要看真实网页/App 走真人测试）；我们准备把浏览器采集做成开源能力，但必须披露“UI vs API”的差异。

## 7. 边界

- 无头 Chrome 只用于“静态 HTML 无文本”的回退，不绕过登录、验证码或反爬；
- 不保证抓到 JS 之后才加载的内容（如需要滚动、点击、登录）；
- 渲染会增加时间与资源消耗，单次研究最多 25 秒；
- 页面文本是来源证据，不是已核实事实；描述缺失时留空，不补写。

下一步：把浏览器渲染扩展成可选的“采集 adapter”（单引擎、可配置地区/账号），并把每次渲染的耗时、UA、最终 URL 记进证据。
