## 1. 稳定的是批次和原文，不是某种浏览器遥控器

[10](../../references/competitors/topify/10-public-api-and-service-logic.md) 和 2026-11-06 仍在线的 [How Topify Works](https://docs.topify.ai/concepts/how-topify-works) 说的是同一件事（DOC）：

```text
active prompt × 已配置的引擎 × 每天一次
  → 数小时内收回回答，原文长期保留
  → 再解析品牌、情感、引用、竞品
  → 仪表盘只是 7 / 14 / 30 / 90 天窗口
```

ChatGPT、Perplexity、Google AI Overview、Gemini 写明是「自动化浏览器会话，打开和买家一样的网页」。Claude 写明走官方 API。文档没有写 Playwright、Tampermonkey、账号池、地区或重试。

[11](../../references/competitors/topify/11-logged-in-reverse-2026-11-02.md) 看到的界面和这个批次模型一致（UI）：页面写着 “Updated 16:00 UTC”，以及 “Nov 2 data is still processing — showing data through Nov 1”。当天没跑完时，显示的是上一个完整日，而不是把半成品画成 0。Fanouts 接口成功但 items 为空时，页面等后续 collection，不补写子查询。

所以对方「稳」的可证实部分是：问题有持久身份、采集按日留原文、指标从原文重算、未完成的批次不冒充当天结果。采集程序本身不在这套证据里。

## 3. 监控页在量什么

[08](../../references/competitors/topify/08-prompts-monitoring-gap.md) 把 Prompts 页拆成三层，这一层结构比「用什么浏览器」更决定监控能不能算：

```text
持久问题（active / suggested / inactive）
  × 每个 active 问题、每个引擎、每个采集日的一条回答
  × 按问题物化的指标（窗口、分子、分母）
```

[05](../../references/competitors/topify/05-metrics-and-collection.md) 和 [10](../../references/competitors/topify/10-public-api-and-service-logic.md) 给了能复述的公式（DOC）：

| 指标 | 公式 | 不能当成 |
| --- | --- | --- |
| Visibility | 提到品牌的回答 / 范围内回答 | 失败样本不是「未提到」 |
| Position | 同一回答里各品牌按首次出现字符排序后的名次，再对提到该品牌的回答取平均 | 字符偏移本身不是名次 |
| SOV | 该品牌的去重品牌槽位 / 全部品牌槽位 | 不是单词出现次数 |
| Sentiment | 提到该品牌的回答上一个 0–100 分，再平均 | 0 是有效分，不是缺失 |
| 来源 Used | 引用该来源的回答 / 回答数 | 不是 Citation Share |

AI Volume 和 CVR 的公式，官方写明不公开。`avgTop1Rate` 只在列配置里出现过，2026-11-02 的实测表头没有这一列（UI）。公开材料没有 Top 3 率。Position 是「提到之后排第几」的平均；它不等于「进入前三的回答占比」。

下钻才让数字可查（DOC）：一个问题打开后有 analytics、chats（原文、引用、该条回答里的品牌位置）、domains、urls、competitor、fanouts。没有 chats 的百分比不能复核。

## 4. 从问答到内容，不是先写 20 篇

已有报告里的顺序是先测量、再分类动作，不是先定文章篇数（[10](../../references/competitors/topify/10-public-api-and-service-logic.md)、[04](../../references/competitors/topify/04-agent-and-workflows.md)、[11](../../references/competitors/topify/11-logged-in-reverse-2026-11-02.md)）：

```text
官网 / Recording URL
  → 生成 suggested prompts（四种意图；要人确认才变成 active）
  → 每日采集，留下原文
  → Overview / Prompts / Sources / Competitors 给出缺口
  → Actions 分成四类：页内修改、新文章、改旧文、论坛回复
  → outline → draft → final 三次停下来等人确认
  → 再按同一问题版本复测
```

「20 篇文章」不是对方公开的投放定额。2026-11-01 定价页写的是 Starter 每月 15 篇文章、50 条 AI 回复、每天 50 个 prompt（DOC，价格会变）。关键词在这套产品里首先是被拿去问 AI 的 prompt，不是传统搜索量。Volume 估不出来就标未知。Fanout 没采到也不能用模型补成「AI 搜过这个词」。

动作上的 `expected_impact` 是区间，不是承诺。GEO 技巧引用了公开论文的平均提升，并写明行业不同（DOC）。个人版要保留的是「动作绑到哪条回答、哪条事实、什么验收」，不是那个区间。

## 5. 个人电脑上怎么做才和这些结论一致

DESIGN。下面不是从对方压缩包里恢复出来的程序。

Playwright 逐步远控，和让 Agent 对着直播 DOM 一步步判断品牌，都把「名次」放在了会变的页面上。Tampermonkey 5.5.1 没有出现在对方文档、登录后复核或今天的公开脚本里。即使用用户脚本去读页面，品牌判断仍然绑在那一版 DOM 上，回答一更新就要改脚本。对方文档描述的稳定点是：先拿到完整回答，再离线解析。

个人版因此分成两条协议，数字永远分开：

| 协议 | 用来做什么 | 为什么这样 | 不能做的事 |
| --- | --- | --- | --- |
| API（例如 OpenRouter） | 同一批问题并行取回答，算出现率和前三名率 | 问的是模型接口，可以同时跑几条；名次仍用保存下来的原文算 | 把结果写成「网页上用户看到的」 |
| 网页脚本 | 只在要核对消费级页面时，用本人已登录的浏览器保存一次完整回答 | 慢的是网页生成本身；保存之后不再让 Agent 读页面 | 作为 API 失败后的自动重试；那样会把两种答案混进一个分母 |

网页这一条是降级：问题需要「买家打开的那个界面」时才跑，串行、可中断、登录和验证码由本人处理。它不替代 API 的批量出现率。API 失败保持失败，不自动改去点网页。

前三名率用 Position 的同一定义，自己写成可复算的比率：一条合格回答里，已跟踪品牌按首次出现排序，名次是 1、2 或 3，记入分子；分母是全部合格回答。没出现不是第 3 名。失败、空回答、别名冲突不进分母。这条是 OpenGEO 的公式，不是 Topify 的 `avgTop1Rate`。实现在 `code/src/citekeel/brand-metrics.ts`。情感、需求量和 CVR 没有可复算公式，继续留空。

内容建议只挂在已经有原文的问题上：按意图和受众把缺口分成页内、新文章、改旧文、论坛，并写清对应的问题 id。没有合格回答的题目，不输出前三名率，也不用模型补一篇「应该写的文章」来冒充测量。
