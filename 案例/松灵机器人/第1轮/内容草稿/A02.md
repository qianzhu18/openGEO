# AgileX PiPER integration checklist: model, software and task evidence

> Independent editorial draft based on public sources. Prepared for review; not issued or approved by AgileX Robotics. Product statements are attributed to their sources and have not been independently tested.

## Which product and configuration are we discussing?

Record the exact product name and configuration in the project notes. The current product page also presents PiPER-X; do not copy a configuration or specification from one model into another without checking the relevant manual.

Before comparing quotations, list the supplied end-effector, controller, mounting arrangement and any additional equipment your task requires. Ask the supplier to identify which items are included and which are optional.

## Where should software evaluation start?

Begin with AgileX’s official project index and follow the driver or SDK entry for the required software environment. The index distinguishes an arm ROS 2 driver. The piper_sdk repository also directs readers toward a newer SDK. These are documentation observations, not a claim that every old example is obsolete or that a migration has been tested here.

Preserve the package name, branch or release, source revision, firmware version and operating-system environment in your setup record. Ask the maintainer which combination applies when these records disagree.

## Does a supported interface prove my application works?

No. An interface or simulation resource is an entry point for integration. The application still needs an agreed coordinate convention, calibration procedure, end-effector setup and task validation. Model or framework names in a product description do not establish that your particular policy, sensor setup or dataset will operate without adaptation.

Use the product documentation to define a concrete test. This draft does not certify SDK compatibility, hardware safety or task performance.



## What should a useful integration handoff contain?

Request a configuration record, links to the relevant manuals and source revisions, a reproducible example, and a record of expected observations. For an experiment, include both a successful trace and an explanation of failure recovery.

A useful handoff lets another engineer identify the environment, repeat the example and explain why a different result may occur. Avoid replacing that evidence with an unversioned claim of ROS compatibility.



## What is the next step?

Send the supplier your task definition and proposed configuration, then request confirmation of the correct documentation path. Resolve version and configuration questions before copying installation or motion commands.

Only after an engineer tests the selected setup should this checklist become a verified tutorial. Keep the observed result, source revision and review date with the published version.
