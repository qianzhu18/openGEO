# How to choose a robot arm for imitation-learning data collection

> Independent editorial draft based on public sources. Prepared for review; not issued or approved by AgileX Robotics. Product statements are attributed to their sources and have not been independently tested.

## Start with the experiment, not the specification sheet

A useful first question is: what repeatable experiment must the lab complete? Define the object, contact task, workspace and desired observations before comparing arms. A precise placement experiment, a demonstration-collection session and a mobile manipulation study create different requirements.

Write a short task card: initial object state; desired final state; allowed human assistance; what counts as failure; and what must be recorded. This gives suppliers a common question to answer. It also prevents a polished demo from becoming the acceptance test.



## Check the complete collection workflow

Hardware choice is only one part of the decision. Ask how demonstrations are captured, reviewed and organized, and how the recorded task will be reproduced. AgileX’s public data-collection page describes those workflow stages. Treat that description as a starting point for questions, rather than proof that a particular dataset will work for your policy.

Source: [具身智能数据采集解决方案](https://global.agilex.ai/pages/agilex-embodied-ai-data-collection-solution)。

## Turn software support into a versioned evidence list

For each candidate, record the exact model, firmware, control interface, software package and source revision. Request the documentation for that combination. A compatibility label does not explain camera calibration, action conventions, end-effector configuration or the data format your training code expects.

AgileX lists development and simulation interfaces for PiPER. Its project index and SDK repository are useful entry points; check which maintained package applies before following an older tutorial. This draft has not tested a robot or executed those interfaces.

## Use a small acceptance experiment

Choose one representative task and agree on its conditions before collection. Preserve the complete trial record, including unsuccessful attempts, resets and operator interventions. Keep the initial state and object variations explicit.

The useful output is a reproducible record, not a single success clip. A proposed trial sheet can contain: task ID; hardware and software versions; configuration; attempt outcome; intervention; failure explanation; and a link to the original recording. Set acceptance thresholds with the research team; this guide supplies no invented success rates.



## What to request before a purchase decision

Ask the supplier for the correct product manual, a versioned integration example, the recording schema, an explanation of how failures are handled, and a demonstration under your conditions. Check what is included in the delivered system and what your team must integrate.

If PiPER is on the shortlist, continue with the integration checklist linked to this guide. Use the same questions for every candidate. Choose based on the task evidence and integration work your lab can support, rather than a generic claim that one arm is best.
